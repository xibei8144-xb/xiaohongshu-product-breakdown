# 内容与文案规则

## 1、信息先于套话

主线：**谁遇到什么问题 → 给产品什么输入 → 怎样交互 → 得到什么结果 → 什么条件会影响结果**。依据读者对该产品的熟悉程度取舍，不机械复述所有环节。

- 每页一个具体问题，标题先给结论，正文分块展开。每块有功能事实、使用例子、差异或限制；“更智能、更高效、赋能工作”等空话不能独立成块。
- 信息量靠独特事实、可比较维度和完整例子增加，不靠字数、术语或重复免责声明增加。页内的概述、卡片和结尾避免三次说同一件事。
- 适用场景写“做什么、产出什么”，不只写“适合产品经理／创作者”。例如“把三款工具按导出格式和编辑能力整理成对照表”。
- 例子在当前内容里讲清楚，读者无需另搜视频或作品才能理解。未实际运行的提示词、流程和结果设想标为编辑示例；不要编造输出当证据。
- 用户举例通常是在说明所需表达方式，除非明确要求，不把这个例子变成整篇的唯一主题。

常用模块按内容选取：用途、代表能力、真实界面、操作路径、关键机制、相关对照、适用条件、产品观察。没有信息支撑的模块直接合并或删除，不预设“四个亮点、三类人、三步流程”。

## 2、不同产品的拆解重点

| 类型 | 优先讲什么 | 容易跑偏的地方 |
|---|---|---|
| 模型 | 哪种任务表现突出；用易懂例子解释复杂指令、生成质量、等待与修改体验；证据支持的进步 | 对熟悉模型的读者重讲“Agent 能干什么”；只堆跑分；把传闻当实测 |
| 创作工具 | 能做哪类成品；输入、生成、修改、导出之间怎样衔接 | 只讲模型和工作流术语，不让用户知道拿它做什么 |
| Agent | 能接什么工作；跨工具执行、上下文、技能、例行任务和交接怎样协作；关键人工环节 | 把所有助手写成“AI 员工”；未经验证承诺省 token、无限后台运行或完全自治 |
| 搜索／知识 | 信息来自哪里，怎样整理、引用与追问；如何回原文核对；与普通搜索的关系 | 把有引用等同于准确，把经验推荐写成客观保证 |
| 具身智能 | 具体本体和可见功能、目标群体、场景、型号差异、现阶段能与不能做的事 | 把介绍写成验收测试清单；混用旧型号、选配、演示与量产能力 |

- 对比围绕本次主角。选择与用户问题相关的少数维度，解释优势及必要条件；公正不等于每段补一句竞品也很好。无证据不宣布全面领先。
- 机器人需分清本体、控制模型与应用方案；受控演示不证明所有环境都能完成。可靠性、人工介入等数据只在有依据且有助理解时写。
- 抽象或节日创作按用户明确要求做，比喻与科学事实分开；别把科学趣味类选题强套完整的软件功能模板。

## 3、证据和平台判断

重要事实记录 `claim / source_url / accessed_at / version_or_scope / evidence_type / caveat`，素材记录文件与来源、展示性质、裁切用途。可写成简短条目，不必为每句常识建表。

- 未实际操作，不能写“亲测、用了几天”。官方展示数字不作自己的测试结论；具体型号、功能灰度和权限条件按来源说明。
- 推荐“认可度高”的产品时说明依据，如用户规模、客户案例、销售或部署记录；热度和演示数量不能直接当作市场份额。
- 推测、观察与建议直接标明。来源链接留在研究记录，不让正文变成外链目录；一次总说明加必要图注即可，不在每页重复大段免责声明。
- 用户问敏感、违规、限流时，查当前官方规则并说明适用范围。区分客观信息、营销宣传、交易导流；不能把“出现价格／某个词”直接断言为违规，也不承诺一定过审。
- 不主动加购买、代充、私信领取、二维码或站外交易话术。价格按用户要求和内容必要性取舍，不默认占独立页面。

## 4、配套发布文案

读者是小红书用户。正文可以独立读懂，补足图片的重点，不照抄整套图片，也不写长篇泛评。

1. 一个主标题，明确产品和切入点；避免无依据的“封神、吊打、必看”。
2. 开头一两句说清实际问题和本次产品价值。
3. 通常用 3—5 个编号短段，每段回答一个问题，如“能做什么／最有区别的能力／怎么用／适合什么情况”。各产品按内容调整，不强制全部出现。
4. 用具体例子解释优势。模型受众已有基础时直接讲增量；面对大众创作工具时先讲可做的作品。
5. 少量 emoji 做段落定位；6—10 个相关 Tag，避免装饰堆砌。正文加 Tag 通常控制在 1000 字符以内，短内容不凑长度；用户指定范围优先。
6. 标题、正文、Tag、研究来源分区保存，方便复制。无实测时简短说明资料性质，按需要说明 AI 辅助制作；不写对话称呼或过度保证。

只要求“文案加 emoji”就改文案；只要求评论回复就给自然、简洁、可直接粘贴的一段话，不展开研究或重出图。
